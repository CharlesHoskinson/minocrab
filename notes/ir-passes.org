#+title: IR passes — but only the ones that buy API

Design of record for the pass work dmd asked for (2026-08-16): *"look at any
optimisation pass (ours or theirs) that can make our API more ergonomic and
composable"*, with the standing criterion from the same conversation —
**only do this if it makes us able to write simpler code, higher up the
stack, which then optimises in a composable way.**

So rows are NOT the objective here. Rows are the constraint: a pass has to
not cost any, and where it happens to save some that is a bonus rather than
the case for it.

* 0. THE MEASUREMENT, first, because it decides most of the argument

"Are we duplicating ZKIR's work?" is not guessable and was not guessed. It
is measured in [[file:../crates/minocrab-contracts/tests/backend_folding.rs][tests/backend_folding.rs]], against Midnight's own cost model
— the same one =row_snapshot= and the benchmark harness use — and committed
so a toolchain bump breaks it rather than silently invalidating this note.

| pattern | rows each | backend folds it? |
|---------+-----------+-------------------|
| =copy= of an immediate | *0* | YES |
| linear op with a constant operand (=add x, 0=) | *0* | YES |
| unused pure instruction | 1 | no |
| duplicated pure instruction | 1 | no |
| repeated =constrain_bits= on the same wire | *2* | no |

Three consequences, and they are most of the design:

** (a) Constant folding above ZKIR buys ZERO rows

Every contortion we have made to avoid emitting a =copy= of an immediate —
M9 phase 7's operand positions, M9 phase 8's inlined guard, M16's
=AnyWire3::immediate=, M17's =UnshieldedToken= — bought DIFFERENTIAL
FIDELITY with compactc. Not cost. Nobody wrote that down at the time, and
the fifth one (changing =LedgerRepr=, which dmd approved on 2026-08-16) was
about to be paid for the same unstated reason.

That does not make the pass worthless. It relocates the case for it: it is
worth building because it lets us DELETE those five special cases, not
because it makes anything faster. Which is exactly dmd's criterion.

** (b) The costliest redundancy is the one that would buy the most safety

A repeated range constraint costs TWO rows — twice a multiply, and more than
any other redundancy measured. That is why the Borsh layer's docs say
"PRECONDITION: the value's leaves are already range-constrained" instead of
just constraining them, and why =Uint::widen= has a paragraph explaining
that it deliberately does not re-constrain.

Those are load-bearing comments standing in for a check, which is the least
composable thing in the codebase: a gadget cannot defend itself, so every
caller has to be right. A deduplicating pass turns that into "constrain
whatever you like, the pass removes what is provably redundant" — safer
code, simpler contracts, and it removes rows rather than adding them.

** (c) Dead code and common subexpressions are real rows, and still not ours

Neither is folded, so both leave rows on the table. Both are nonetheless
rejected below, for reasons that are about correctness rather than value.

* 1. THE CONSTRAINT NOBODY SHOULD FORGET

Our primary correctness warrant is DIFFERENTIAL EQUALITY with compactc —
instruction for instruction, for the M14/M15/M16/M17 fixtures. A pass that
makes us *match* compactc more closely is free. A pass that makes us *beat*
compactc costs us that test, and we know the price because M10 paid it: the
optimised vault proves its own preimage and its warrant is symbolic-effect
equivalence plus a nine-million-case harness instead of PI-equality.

So passes divide cleanly:

| pass | vs compactc | gate |
|------+-------------+------|
| constant folding | DIVERGES by inlining (see §8) | always on, both sides normalised |
| guard scoping | neutral (same stream) | always on |
| constraint dedup | DIVERGES | opt profile, M10 warrant |
| dead code elimination | diverges | rejected, see §3 |
| common subexpression elimination | diverges | rejected, see §3 |

* 2. THE THREE TO BUILD

** (i) Guard scoping — the biggest API win, and not the backend's job

Every ledger and kernel operation takes a guard operand, so every method has
an =_under= twin differing only in that argument. =minocrab-std/src/v3/
kernel.rs= is about half boilerplate for this reason, and =ledger.rs= worse.

It also does not COMPOSE, which is the real complaint. A helper called under
a branch has to thread the guard through its entire call graph by hand;
=send_unshielded= has to know that =is_self= needs a guard, and =is_self=
has to know that =kernel_self_guarded= exists. Nesting two guarded regions
means anding the conditions manually.

What we want:

#+begin_src rust
c.guarded(cond, |c| {
    kernel::inc_unshielded_inputs(c, &token, amount);   // the PLAIN form
});
#+end_src

Implementation is a splice, not an optimisation: emit the body into a
sub-buffer, then rewrite the guard operand on every Impact instruction and
every =public_input= gate as it merges back, anding with any enclosing
guard. The instruction stream is IDENTICAL to what the =_under= form
produces today, which is what makes this safe to turn on everywhere — the
differentials cannot tell the difference, and that is the point.

Deletes: the =_under= half of the ledger and kernel APIs, and the
=_guarded= variants beside them.

** (ii) Constant folding — as normalisation, with the case restated

Fold =copy= of an immediate into its consumers and drop the =copy=. Zero
rows either way (§0a); the value is that it subsumes all five special cases
and future operand positions get it for free.

Consequence worth stating plainly: *the =LedgerRepr= change dmd approved
should not be made.* The pass gives the same output with no trait change and
no churn in the four vault forks. =UnshieldedToken= can go back to being an
ordinary =Either=, and =AnyWire3= can go back to carrying a =Val=.

The =impl Into<Operand>= ergonomics STAY — writing =c.add(x, 1u64)= is nicer
than naming a constant regardless of what it lowers to. What goes away is
its NECESSITY, and the pressure to add another one every milestone.

** (iii) Constraint deduplication — the sleeper

Track, per wire, the tightest =assert_bits= already emitted; drop a later
=assert_bits(w, m)= when =m >= n= for an already-emitted =n=. Sound in that
direction only: a wire constrained to =n= bits satisfies any wider bound,
which is exactly the argument =Uint::widen= already makes for why widening
needs no new constraint.

This is the one that changes what code you can write. Gadgets become able to
assert their own preconditions, so the Borsh layer's "PRECONDITION: already
constrained" comments become checks, and getting it wrong becomes impossible
rather than invisible.

DIVERGES from compactc (which re-emits), so it goes behind the opt profile
with M10's warrant. Rows go DOWN, which is the direction that profile
already wants.

* 3. THE TWO TO REJECT, and why

** Dead code elimination — unsound here without care nobody will maintain

=constrain_bits=, =assert=, =impact= and the transcript gates have no
dataflow consumers. A pass that drops instructions "nothing uses" removes
range checks, and a missing range check is invisible to every differential
test on an honest preimage — the exact failure mode M12 stage 1 centralised
=CircuitArg::constrain= to prevent.

It is implementable with an effectful-op deny-list. It is not worth it: one
row per dead instruction, and we do not emit dead instructions, because the
eDSL only emits what a gadget asked for.

** Common subexpression elimination — needs protocol arguments a pass cannot make

M10 rung i is the proof. The optimised vault reads =kernel.self()= once and
threads it, where compactc reads it at every call site. That IS legitimate —
the address is constant for the transaction and every emitted read still
reconciles through =ResultModeVerify::process_read=, so read count is
"framing, not protocol" — but M10 made that argument explicitly, and still
left =claim= and =completeWithdraw= alone.

A mechanical CSE pass has none of that context. It would dedupe ledger reads
and change the transcript. Where CSE is right it is a TYPED decision, made
in a gadget by someone who can write the soundness paragraph.

* 4. THE GENERAL SHAPE, since it keeps recurring

The wins that actually moved the benchmark — 35-58% in the M10 fork, nine of
twelve k-boundary crossings — came from INSTRUCTION SELECTION: native
=ReverseBytes=, byte-aligned slices instead of per-byte div_mod chains, the
segment-based serializer. Every one needed to know a value was a =Bytes<32>=
with a known alignment.

ZKIR is type-erased. A pass over it sees field elements, so for the
optimisations that matter it is working with strictly less information than
the eDSL has. That is the standing reason to keep OPTIMISATION in the typed
layer and use passes only for things that are genuinely uniform.

Guards are uniform. Constants are uniform. Range constraints are uniform.
Instruction selection is not, and never will be.

* 6. GUARD SCOPING, as built

=Circuit3::guarded(cond, body)= sets an AMBIENT GUARD for the closure. Three
things pick it up, and the third is why this is a safety feature rather than
a convenience:

1. Impact instructions.
2. Public-transcript reads — so a read inside a scope needs no =_guarded=
   variant.
3. *Witnesses* (added 2026-08-16). A guarded private input yields the
   default and does NOT consume the private transcript when its guard is
   false, so an unguarded witness inside a branch consumes a value on the
   path not taken. Semantic, not framing — and invisible to a differential
   on an honest preimage, like the assertion case below.
4. *Assertions.* =assert(x)= inside a scope lowers as
   =assert(select(guard, x, 1))=. By hand this is the caller's job, recorded
   only in a doc comment ("asserts inside the branch are the caller's job"),
   and getting it wrong makes the assertion fire on the branch that was NOT
   taken — which no differential test on an honest preimage can see. That
   bug class is now unwritable inside a scope.

THE GATE, and the reason it is safe to adopt incrementally:
=tests/v3_guard_scope.rs= proves =guarded(g, plain)= is BYTE-IDENTICAL to
the hand-threaded =plain_under(g)= for every shape — Impact ops, reads,
assertions, nesting, and =if_else=. It is a way of writing the guard down,
not a different lowering. All 164 pre-existing circuits are unchanged
(zkir_dump: 0 files differ).

NESTING IS COMPACT'S =&&=, and this is the part that pays. The conjunction
is computed ONCE on entry, and a read between two scopes is guarded by the
OUTER one alone — which is exactly the shape M17's =sendUnshielded= needed
and which I had to reverse-engineer from compactc's artifact to write by
hand. It now falls out of writing the code in the shape of the source.

** ONE SPELLING (dmd, 2026-08-16)

The API arrived at six entry points for one concept — =Circuit3::guarded=,
=if_else=, =when=, =when_value=, =predicate::guarded=,
=predicate::if_else= — which is exactly the sprawl this work exists to
remove. It is now TWO:

| =c.when(cond, body)= | effects. Chain with =.else_when= / =.otherwise= |
| =c.when_value(cond, body)= | a value. =.otherwise= is mandatory and returns it |

- =guarded= is PRIVATE plumbing. It returned the body's value, which invites
  the reading that the value came from a conditional — when in fact it was
  computed unconditionally and only its EFFECTS were guarded. A value that
  depends on a branch has to be SELECTED, which is =when_value=.
- =if_else= is gone: =when(a, ..).otherwise(..)= is byte-identical to it,
  proven before the removal, so it was sugar for a two-arm chain.
- The =predicate::= pair is gone because =Check= implements =GuardCond=, so
  =c.when(eq(x, y), ..)= already works.

AND THE CONSOLIDATION FOUND A BUG. With =when= as the plain-guard spelling,
=c.when(cond, body);= is a statement — and the chain builder was computing
its "nothing matched yet" accumulator eagerly, so a plain =if= with no
=else= emitted a =cond_select= nobody used. Per =backend_folding.rs= an
unused instruction is a REAL ROW and the backend does not drop it. The
accumulator is now computed only when another arm actually arrives, and
=a_bare_when_emits_no_accumulator= pins it.

Worth noting how that was caught: not by review, by the measurement table
from §0 being close at hand.

** dmd's two questions, both yes

*THE PREDICATE VOCABULARY IS THE GUARD VOCABULARY.* =predicate::guarded(c,
eq(a, b), ..)= — =Check='s =and= / =or= / =not= compose into guards for
free, and a comparison's WIDTH is resolved from its operand types in one
place rather than two. A condition is a condition; whether it lands in an
=assert= or in an Impact guard operand is the caller's business.

*IF/ELSE EXISTS*, =Circuit3::if_else= (and the chain below), with the negation
(=select(cond, 0, 1)=, compactc's own =!=) computed once. Both arms emit all
their instructions — a circuit does not branch, so cost is the sum. That is
the setting, not a choice.

** …and the third question: can two nested guards become one statement?

There WAS a =guarded_all(c, &[&|c| .., &|c| ..], body)= — a flat spelling of
nested scopes, each conjunct evaluated under the ones before it. It is
REMOVED (dmd, 2026-08-16), and the reason is better than "redundant".

The flat list hides exactly the fact that matters. The nesting is not
incidental: it IS the short-circuit structure of Compact's =&&=, and in
=recipient.is_left && recipient.left == kernel.self()= the second conjunct
performs a TRANSCRIPT READ that compactc guards by the first. Written
nested, that is visible in the shape of the code. Written flat, it looks
like a list of independent conditions and the evaluation order — the whole
subtlety — is invisible.

So: nest. Two lines and an indent, and the indent is carrying information.

A GENUINELY flat conjunction — =guarded(c, a.and(b), ..)=, both sides
evaluated up front — is available and correct whenever the conjuncts are
PURE. For the self-address case it would mean reading =kernel.self()=
UNGUARDED, which M10 rung i already established is sound (read count is
"framing, not protocol"; every emitted read still reconciles through
=process_read=). That costs the differential and therefore belongs in the
opt profile — which is exactly the split §1 predicts, arriving from a
direction nobody planned.

** …and the fourth: an if / else-if / else CHAIN

=c.when(a, ..).else_when(b, ..).otherwise(..)=, arms MUTUALLY EXCLUSIVE —
arm /n/ runs where its own condition holds and no earlier one matched.

The mechanism is one accumulator wire, "nothing has matched yet". Arm /n/'s
guard is =unmatched && cond=; the accumulator then becomes
=unmatched && !cond=, which is ONE =cond_select= rather than a negate and an
and (=select(cond, 0, unmatched)=). So two selects per arm after the first,
and BOTH ends are free: the first arm's guard is its condition, and
=otherwise='s guard is the accumulator itself.

Falls out of that: a two-arm chain is EXACTLY =if_else=, one negation and no
more (=a_two_arm_chain_is_if_else= pins it). And a chain nests inside a
guard — its arms conjoin with the ambient one, so an if/else-if inside a
branch needs no threading either.

Arms return =()=, deliberately. A circuit does not branch, so every arm's
instructions are emitted regardless and "the value of the branch that ran"
is not something the stream can express; build it with =cond_select= on the
arms' results, where the selection is visible and priced.

** …and the fifth: the chain as an EXPRESSION

=c.when_value(a, ..).else_when(b, ..).otherwise(..)= returns a value —
Compact's =if= as an expression. dmd asked for it knowing it is expensive,
and wanted the cost stated rather than the feature withheld. Both are done;
the cost is in the method's own docs, where a caller will meet it.

EXHAUSTIVE BY CONSTRUCTION, which the effectful form does not need and
cannot have: =otherwise= is the only method that returns the value, so a
value chain without a fallback does not compile. An arm that does not run
simply has its effects guarded off; a value has to come from somewhere.

THE COST, stated honestly in three parts:
- Every arm's instructions are emitted regardless. An =if= costs the SUM of
  its arms, never the maximum. That is the setting, not this API.
- One =cond_select= per NATIVE SLOT of the result, per arm — so a
  =Bytes<32>= is two, and a =Maybe<T>= selects its tag as well as its
  payload. =Select= is the trait, implemented for the typed leaves.
- The two selects the guard accumulator already costs.

AND WHAT IT DOES NOT COST: anything over the hand-written form.
=a_value_chain_is_the_hand_written_select= pins that — the selects are the
ones a careful author writes anyway. What the abstraction removes is
selecting on the wrong guard, and the temptation to skip guarding the arms'
EFFECTS because only the value looked conditional
(=a_value_chain_still_guards_effects=).

So the recommendation is not "avoid it". It is: reach for it when the
branches genuinely produce a value; reach for straight-line code and one
=cond_select= at the end when one arm is much dearer than the other and you
would rather pay for that arm once, unconditionally.

=otherwise= returns =Selected<T>= (dmd, 2026-08-16) — =repr(transparent)=,
=Deref= to the value, =Copy= where the value is, =into_inner()= to be rid of
it. Field access needs no ceremony: a =Selected<B32>= still has =.hi=.

It exists for one reason a function-level =#[must_use]= cannot serve. A
function attribute fires only where the call is WRITTEN; a must-use TYPE
fires wherever a value of it is dropped — including one step removed, which
is where the waste actually happens:

#+begin_src rust
fn fee(c: &mut Circuit3, ..) -> Selected<Uint<64, Public>> {
    c.when_value(..).otherwise(..)     // fine, it is returned
}
fee(&mut c, ..);                        // …and THIS is the mistake
#+end_src

A compile_fail doctest on =Selected= pins exactly that shape.

THE TENSION, recorded because it decides how much the wrapper is worth: the
more eagerly it is unwrapped, the less it propagates. Kept in a helper's
SIGNATURE it catches the dropped-result mistake a caller away; unwrapped at
the first opportunity it degrades to the function-level attribute it
replaced. Both are acceptable — the type also reads as documentation at
every use site ("this came from a branch, so every arm was paid for") — but
the LINT only pays if signatures keep it. That is a convention question for
the ported contracts, not something the type can enforce.

NOT CLAIMED: that an /n/-arm chain matches compactc's lowering of an
=else if= ladder. No fixture exercises one, so the two-arm case is checked
against =if_else= and the /n/-arm case against a hand-written expansion.
That gap is worth a fixture when a corpus contract needs it.

A GENUINELY flat conjunction — =guarded(c, a.and(b), ..)= with both sides
evaluated up front — is available and correct whenever the conjuncts are
PURE. For the self-address case it would mean reading =kernel.self()=
UNGUARDED, which M10 rung i already established is sound (read count is
"framing, not protocol"; every emitted read still reconciles through
=process_read=). That costs the differential and therefore belongs in the
opt profile — which is exactly the split §1 predicts, arriving from a
direction nobody planned.

* 7. EVIDENCE FROM M17's SHIELDED PORTS (2026-08-16)

Three ports written to compactc's own instruction stream, and every place
they could NOT go through the ergonomic API is evidence for §2. Recorded
here because it arrives from a direction §1 did not anticipate: not "the
backend already folds this", but *the surface API can only be as ergonomic
as the lowering allows, while the bar is instruction equality*.

1. *=!b= is a =cond_select=, not our =not=.* compactc has no boolean-negation
   opcode; it emits =cond_select(b, 0, 1)=. =minocrab_std::v3::kernel= has
   carried a private =not= of exactly that shape since stage 2, and the
   shielded ports use it twice more. Our =Circuit3::not= emits ZKIR's =Not=,
   which is correct, one row, and never what compactc writes.

2. *=&&= is a =cond_select=, and =predicate::and= is a =mul=.* Both are right
   on booleans and both cost one row. But a circuit that must match
   instruction for instruction cannot use the predicate vocabulary for a
   conjunction, so =bytes_eq= and =is_self= hand-write the select.
   Note this one is NOT a pass's job: =mul= on two arbitrary field elements
   is not a select, so a pass over type-erased ZKIR may not rewrite it. It is
   a TYPED decision — =Check::and= knows its operands are booleans — and
   therefore §4's rule says it belongs in =predicate.rs=. Changing it would
   move instructions (not rows) in every circuit that guards through
   predicates, so it wants its own commit and its own dump diff.

3. *A folded tag beats a chain.* =sendShielded= ends in Compact's =if= as an
   expression, which is what =when_value= is for, and it still cannot use it:
   compactc folds the =Maybe='s tag into the else-arm's guard, because
   selecting between the constants 0 and 1 IS that guard. The chain would emit
   the select a second time. Constant folding (§2 ii) does not fix this one
   either — the inputs are constants but the SELECT is what has to disappear,
   which is a peephole on =cond_select(b, 0, 1)= → the guard wire itself.

So §2(ii) grows a sibling worth naming: a *boolean normal form* — fold
=cond_select(b, 0, 1)= to =b='s negation-of-record and recognise the shape
when it is asked for a second time. Cheaper than it sounds, because there are
only two spellings in play and both are already written down here.

MEASURED, since both classes now have a number
(=minocrab-sim/examples/opcost.rs=, new cases): 100 =copy=s of an immediate
cost ZERO rows; 100 =cond_select=s cost 101. So constant folding (§2 ii) is
worth exactly its instruction count and no rows — which §0(a) already said —
while a select that a fold could remove is one row each. Both remain small;
the case for the passes is API surface, not cost, exactly as §2 argues.

* 8. CONSTANT FOLDING, as built (2026-08-16)

=minocrab_ir::v3::passes::fold_immediate_copies=, run by =Builder3::finish=
so every circuit gets it: a =Copy= of an immediate is substituted into its
consumers and dropped. 768 =copy= instructions removed across 91 of the 167
workspace circuits; the other 76 had none. Zero rows, as §0(a) measured —
row_snapshot is bit-identical and the interface snapshot untouched.

** §1's table was WRONG, and the fixture that proved it

The table said constant folding CONVERGES on compactc. It does not:
*compactc names some of the constants it inlines elsewhere*, and the naming
is driven by its own frontend rather than by any operand-position rule.
M17's =sSendShielded= is the counterexample —
=upgradeFromTransient='s zero high limb is emitted as =copy 0x00= and then
used BOTH as a hash operand and, through a =cond_select=, as an output. An
always-on fold makes us strictly MORE inlined than compactc, which costs the
instruction-for-instruction fixtures.

An "all uses are operands" rule does not save it (that was tried first: the
change coin's zero limb reaches the output only through a select, so the rule
folds it and the fixture still fires). The naming is not a property of the
ZKIR at all.

*APPROVED (dmd, 2026-08-16)*: /"I'm fine if the naming of constants changes,
obviously provided that doesn't cause changes to program behaviour, assuming
the user doesn't hand code pointers to state (which we shouldn't expose as an
option)."/ Both conditions are structural rather than conventional, and were
checked at the point of approval rather than assumed:

1. *NO CALLER CAN HOLD A POINTER INTO THE WIRE NAMESPACE.* =Circuit3='s
   =b: Builder3= field is private and there is no accessor; =Wire3='s =val=
   is private; =Builder3::identifier= has exactly ONE caller in the whole
   workspace (the disclosure recorder, below). A contract cannot obtain,
   store or hard-code a wire name, so there is nothing for a rename to
   invalidate. The option dmd says we should not expose is not exposed.
2. *THE TWO OUT-OF-BAND HOLDERS ARE BOTH HANDLED, AND THEY ARE THE ONLY TWO.*
   - The =Output= terminator: =returned_identifiers= excludes any identifier
     appearing there, so a constant a circuit RETURNS keeps its name on both
     sides. This is the one position where a wire name is externally
     meaningful.
   - The disclosure record: =disclosed_wire= asks =immediate_of= at RECORD
     time and stores =DisclosedWire::Constant(imm)= rather than a name the
     pass is about to remove.
   Everything else that maps identifiers — the simulator's =memory=,
   =rowcost='s type inference, =minocrab-abi='s input names — DERIVES its map
   from the (already folded) stream rather than holding one across =finish=.
   Inputs are never =Copy= outputs, so the ABI is untouched.

*THE RESOLUTION*: the four instruction-for-instruction differentials
(=kernel_tokens=, =adts=, =bounded=, =opaque=) run the SAME fold over
compactc's artifact before comparing. Their criterion becomes "identical
instruction for instruction, MODULO the naming of constants" — and that is a
precise, mechanically defined relation rather than a weaker one: everything
else still compares exactly, the normaliser is the pass itself (one
definition, not a test-local approximation), and a =copy= of an immediate is
a rename with zero rows, no public input and no semantics. *This is the one
judgement in the pass that is dmd's to veto.*

** What it bought, immediately and without being asked

- =opaque_differential= lost its bespoke =without_named_immediates=
  normaliser, its =NAMES_A_LITERAL= list and a whole test that counted the
  extra =copy=s. All fourteen circuits are now equal on the same criterion as
  each other. M15 left that gap open pending an API change to =LedgerRepr=
  that all four vault forks depend on; *that change is now unnecessary*,
  which is §2(ii)'s prediction landing exactly as written.
- =erc20_vault_modern='s divergence ledger collapsed to =Twin::Identical=
  for ALL NINE circuits. M9 phase 8's showcase twin differed from the borsh
  fork in precisely one class of instruction — the =Copy=s that named a
  constant — so the ergonomic rewrite is now free at the IR level rather
  than merely PI-equivalent. Five are byte-identical; the other four agree
  up to identifier NUMBERING (a removed copy still consumed its number), so
  that ledger's test canonicalises names like every other differential.

** The one thing the fold broke, and what it says about disclosure

A disclosed constant had no identifier left to resolve, so the valued
disclosure report read =<not computed>=. =Disclosure3= now carries
=DisclosedWire::Named(Identifier) | Constant(Fr)= and the simulator resolves
the second directly. That is better than what it replaced: a constant's value
was never in doubt, and the record now says so instead of pointing at a wire.

** THE FIVE SPECIAL CASES: what actually gets deleted, decided by looking

§2(ii) said the pass lets us delete all five. Scoped one by one, the answer is
*the pass deletes the PRESSURE, not the mechanisms* — and one of the five was
the only one that mattered:

1. =impl Into<Operand>= (M9 phase 7) — STAYS, as §2(ii) already said. Writing
   =c.add(x, 1u64)= is better than naming a constant whatever it lowers to.
2. The inlined Impact guard / guard-free ledger methods (M9 phase 8) — STAYS.
   The same thing: an API, not a workaround.
3. =AnyWire3::immediate= (M16) — STAYS, and this is the one that changed my
   mind. Deleting it would let =AnyWire3= carry a =Val= again, at eleven call
   sites that all get MORE verbose (a constant hash operand would need =c= and
   a visibility). Against that it introduces a latent conditional: a constant
   emitted as a =copy= is inlined only if every use is foldable, so a hash
   operand that is ALSO returned would silently keep its name. Today's
   spelling is unconditional. Trading an unconditional guarantee for eleven
   shorter lines is the wrong direction on this project's priority order.
4. =UnshieldedToken='s own =ledger_value= (M17) — STAYS, with a BETTER reason
   than it had. Routing its constants back through the general =Either=
   =LedgerRepr= would emit them as WIRES, and =Circuit3::impact_mixed= records
   a disclosure ("impact public input") per wire and none per immediate. So
   the general path would add disclosure-report lines for values that are not
   disclosures of anything. The type carrying its own constants is not a
   workaround for the fold; it is the thing that keeps the report honest.
5. The =LedgerRepr= change dmd approved on 2026-08-16 (the FIFTH, and the only
   one not yet built) — NOT MADE, and now never needs to be. That was the
   expensive one: a trait change all four vault forks depend on. The pass
   costs it nothing and it is withdrawn.

So the deletion the pass bought is the one that had not happened yet, plus the
two in the TEST layer that did happen (=opaque_differential='s normaliser and
the twin's divergence ledger). The four surviving mechanisms are each
load-bearing for a reason recorded above, and none of them is pressure to add
a sixth: a new operand position needs no special case now, which was the
point.

* 9. STEP 3, as built (2026-08-16): what the scope replaced, and the two
  things it cannot

** The straight-line half went completely, and for free

54 of the call sites spelled an UNCONDITIONAL ledger operation as
=x_under(c, one, ..)=, where =one= is =c.constant(1u64)= — a =Copy= of the
immediate =1= that §8's fold now substitutes into the Impact instruction and

and lost it, which is how the three port forks reached the spelling
=erc20_vault_modern= has had since M9 phase 8.

Worth naming because it is the fold paying a second time: before §8 this
rename would have MOVED every one of those instructions, from a named wire to
an immediate.

** The BLOCK-shaped guard went too, and this is where the scope pays

=refund_surrendered_value= threaded =guard: Wire3= through its signature to

MEASURED, on the criterion the differentials use: 162 of 167 circuits

** WHAT THE SCOPE CANNOT REPLACE (1): a guarded value that escapes its block

27 of the 39 remaining call sites are one shape: a guarded READ or WITNESS
whose VALUE is consumed OUTSIDE the guarded block. =erc20_vault_opt='s merged
=refund= is the clearest — the withdrawal route's record and the swap route's
record are each read under their own guard, and then both feed ONE
=cond_select= in a shared claimant gate. There is no block that contains the
read and its consumer.

=when= returns =()= by decision (§6: a value that depends on a branch has to
be SELECTED, which is =when_value=), and =when_value= is the wrong shape here:
it needs an =otherwise= and emits a =cond_select= per slot, which a guarded
read does not. So the value cannot come out of the scope.

The decision to re-examine is narrow, and it is dmd's:

  A GUARDED READ IS NOT A CONDITIONAL VALUE — it is a value that is the
  type's DEFAULT when the guard is off, with no select emitted. §6 rejected a
  value-returning =guarded= because it "invites the reading that the value
  came from a conditional, when in fact it was computed unconditionally and
  only its EFFECTS were guarded". For a transcript read that reading is not
  wrong, it is exactly right — which is why the objection may not reach this
  case.

*SETTLED, and not the way the question was framed* (dmd, 2026-08-16): the
right move was not to change =when= at all. dmd's objection to the silent
default was stronger than the objection to naming a guard — /"I'm not sure
how I feel about something returning a default value on failure, are there
any ways to make it so the programmer generally has to think about it, but
can do something like ok_or_default()?"/ — and that question has a better
answer than a scope does. See §10.

The rule that fell out: *a read whose value you keep is a read whose guard you
name*, and the value comes back in a =Guarded<T>= that will not let you use it
until you say what the default means. =when= stays effect-only, the =_guarded=
read helpers stay (they are the equivalence twin anyway), and the 27 sites are
no longer a gap — they are the API working.

The other 12 remaining sites are effect-only =remove_under=s, and they COULD
move — as twelve one-statement scopes, interleaved between the reads above
that cannot. They are left alone deliberately, for the reason in the last
subsection: a scope per statement is ceremony, not structure. They move when
the 27 beside them do, or not at all.

** WHAT THE SCOPE CANNOT REPLACE (2): the halves ARE the equivalence proof

The bigger correction, and it is why /delete/ is the wrong verb in step 3.

=tests/v3_guard_scope.rs= proves the scope is a way of WRITING a guard down
rather than a different lowering, and it does so by building the same circuit
twice: once with =guarded(g, plain)= and once with the hand-threaded
=plain_under(g)= / =witness_guarded(g)= / =public_transcript_input_guarded(g)=,
then comparing bytes. =tests/v3_ledger.rs= does the same for the typed ledger
layer against raw =minocrab_ledger= calls. Delete the halves and there is no
twin left to compare against — the test would have to hand-roll a duplicate of
the thing it is checking, which is not a proof of anything.

So the halves are not dead API to remove; they are the REFERENCE
IMPLEMENTATION the gate compares to. The right move is to DEMOTE rather than
delete: they stop being how a contract spells a guard (done — 85 of the contracts'
124 call sites moved), and they stay as the threaded twin the equivalence tests need.
Whether they should also stop being =pub= is a separate and smaller question,
answerable only after the 27 above are settled.

** Where the boundary actually falls, stated so the next session does not
   re-derive it

A scope pays when a whole BLOCK shares one guard: the guard is named once, and
the reads, witnesses and asserts inside stop being able to get it wrong. That
is =refund_surrendered_value= and both routes of the port's =refund=.

A scope does NOT pay when guards alternate statement by statement, which is
what the merged =refund= of the opt lineage is — the withdrawal route's and
the swap route's reads interleaved so their results can be selected. One-statement scopes there would
be more ceremony than the named guard they replace, and would say something
false besides: that the statements form a block.

* 10. =Guarded<T>=, as built (2026-08-16)

A guarded-off gate yields the type's DEFAULT and skips the transcript
(upstream =ir_vm.rs:348-366=). Until now the typed layer handed that value
back as a bare =T= and nothing said so — the silent default was not a gap §9
opened, it was one that had been there since M10's guarded reads landed.

=minocrab::v3::Guarded<T, V>= is what the guarded read helpers return now.
Three ways out, and the price list is =tests/v3_guard_scope.rs=:

| | means | measured cost |
|---+---+---|
| =or_default()= | "the default is the right answer here" | *byte-identical to the bare read* |
| =or(c, fallback)= | "use this instead where the guard was off" | exactly the hand-written =cond_select= |
| =assert_read(c)= | "the guard must have held" | one =Assert= on the guard |

=or_default= being FREE is the point worth stating, because the instinct is
that a type-system win costs rows: the wire already IS the default, so naming
that fact emits nothing. The type is a compile-time statement about a value
the VM already produced.

NOT =Deref=, and the reason is the test this session arrived at for Deref
generally (see the Deref survey in the same session): =Selected<T>= derefs
because it guards against DROPPING a value, where a coercion is harmless.
=Guarded<T>= guards against CONFUSING two values — the read one and the
default one — so a coercion that silently produced the value would undo
exactly what the type is for. =#[must_use]= covers the dropped case instead.

WHAT IT FOUND, which is the argument for having built it: 19 call sites
across the four vault forks were consuming a possibly-default value with
nothing at the type level saying so. All 19 turned out to MEAN

compiler error rather than by reading, and the next one might not be.

One new helper fell out: =kernel::self_address_guarded=, so a contract never
reaches for =minocrab_ledger::kernel_self_guarded= and its raw =[Wire3; 2]=.
That completes the =kernel.self()= unification M18 started — the raw op is
now entirely below the typed layer, guarded and unguarded alike.

Zero movement: 162 of 167 circuits byte-identical, 5 identical modulo
identifier numbering (inherited from §9's commit), 0 changed.

* 11. CONSTRAINT DEDUP, as built (2026-08-16), and what it makes checkable

=minocrab_ir::v3::passes::dedup_range_constraints=, run by =Builder3::finish=
only when =Circuit3::dedup_range_constraints(true)= asks for it. Per
IDENTIFIER it tracks the tightest bound proven so far and drops a later
constraint whose bound is WIDER OR EQUAL; a TIGHTER one is new information and
stays, becoming the bound from there on. Never the first. Never an immediate
operand — a constraint on a folded constant names no wire, so there is nothing
to key on. Nothing is reordered or renamed.

The direction is =Uint::widen='s argument: =val < 2^n= implies =val < 2^m= for
=m >= n=, and never the reverse. ZKIR v3 is SSA (upstream's synthesis
memory is a push-only Vec — =mem_push= —,
=ir_vm.rs= (=mem_push= — the synthesis memory is a push-only Vec, so rebinding is unrepresentable rather than rejected), rejects a second binding), so a bound proven anywhere in
the stream holds everywhere in it and "earlier" only decides which of two
identical constraints survives.

** THE BOOLEAN QUESTION, checked rather than assumed

=constrain_to_boolean= and =constrain_bits(w, 1)= are DIFFERENT GADGETS and
the SAME PREDICATE, and a pass over a constraint system reasons about the
predicate:

- =ConstrainToBoolean= → =std.convert::<AssignedNative, AssignedBit>=
  (=ir_vm.rs= (the ConstrainToBoolean arm, with upstream's own "Yes, this does insert a constraint"), carrying upstream's own "Yes, this does insert a
  constraint"), which assigns a bit and asserts the wire equals it
  (checked in the pinned =ir_vm.rs= itself; the supervisor re-verified the
  arm and its comment verbatim). So =val ∈ {0,1}=.
- =ConstrainBits { bits: 1 }= → =assigned_to_le_bits(x, Some(1), false)=
  (=ir_vm.rs= (the V0-only arm; the CURRENT version's arm is =assert_lower_than_fixed(x, 2^bits)=)), one limb of one bit
  (current-version arm: =assert_lower_than_fixed(x, 2^bits)=; the
  decomposition is V0-only). So =val ∈ {0,1}=.

Upstream's native semantics agree line for line: =resolve_operand_bool=
accepts 0 and 1, =resolve_operand_bits(_, Some(1))= accepts exactly the values
with no bit above the first. So they are ONE FAMILY here, in both directions.

That is not a fine point, it is load-bearing: =Bool='s argument constraint IS
=constrain_to_boolean= (compactc's table, =Prim::Uint { bits: 1 }=) while its
Borsh segment is one BYTE, so the checked serializer's =constrain_bits(_, 8)=
on a bool is dropped only ACROSS the families. Keep them separate and fix 2 is
not free. =booleanity_and_a_one_bit_range_are_one_family= pins both directions
and the asymmetry (booleanity AFTER an 8-bit range is real information and
stays).

** FOLD FIRST, THEN DEDUP

=finish= runs =fold_immediate_copies= and then, if asked, the dedup. The order
is forced in one direction and free in the other:

- The fold changes OPERANDS. A constraint on a named constant becomes a
  constraint on an immediate, which the dedup pass deliberately ignores.
  Running the fold first means every decision the dedup makes is about a name
  the circuit actually ships; the other order keys on identifiers the fold is
  about to remove and reaches a different, weaker answer for the same circuit.
- The reverse dependency does not exist. The dedup only DELETES constraints,
  which bind no name and produce no value, so it cannot invalidate anything
  the fold established.

Same caveat as the fold, inherited rather than introduced: =AssertMessage= and
region indices are recorded at BUILD time, so a pass that removes an
instruction shifts them. Pre-existing since §8; the dedup does not make it
worse and does not fix it. FIXED 2026-10-10, §13.

** WHAT FIX 2 BUILT ON TOP, and why it is a mode rather than a twin

- =Serializer::constrained()= — the same serializer, which emits each
  segment's =constrain_bits= at =8·len= before packing. A MODE, not a checked
  =push_*= twin, for two reasons: the precondition is about EVERY segment (a
  packing with three of four fields constrained is as non-injective as one
  with none, so partial checking would discharge nothing while looking like it
  did), and the pushes come from =CircuitBorsh::push_segments= — including the
  derived ones — which cannot pass a checked spelling through. As a mode,
  every existing impl becomes checked without changing a line.
- =borsh::to_bytes_constrained= is =to_bytes= through it.
- =Split::constrained= / =WitnessCheck::constrained= — the reader's
  precondition is about the BUFFER the caller passes, so the seam is the
  CONSTRUCTOR, and it emits the buffer's own =constrain_input=.
- A LITERAL SEGMENT IS NOT RE-PROVEN. =push_literal= builds its own constant
  limbs, in range by construction — and after the fold a constraint on one
  names an immediate, which no pass can remove again. So constraining them
  would be permanent cost for nothing.
- =hash::persistent_hash= gets no twin, because there is nothing to wrap: the
  check is =constrain_canonical= at the call site, which already exists. Its
  doc now says that, plus the flag that makes it free, instead of stating the
  precondition and stopping.

** THE KEY TEST, which is the whole claim

=crates/minocrab-std/tests/v3_dedup.rs=. One representative record (every leaf
family, including the =Bool= whose entry constraint is booleanity and whose
segment is a byte), built twice:

(a) today's — arguments constrained at entry via =CircuitArg::constrain=,
    =to_bytes= trusting them, no pass;
(b) checked — the same entry constraints, =to_bytes_constrained=, dedup ON.

*BYTE-IDENTICAL SERIALIZED ZKIR.* Not the same rows, not the same count: the
same instructions in the same order with the same wire names. The checked
path's twelve added constraints are exact duplicates of the entry ones and the
pass drops precisely them.

Three tests keep that honest: the check is REAL with the pass on but nothing
else constraining the leaves (the twelve survive — a future widening of the
dedup rule fails there); the COST is real with the flag off (the same twelve,
two rows each); and literals add nothing.

*A FINDING FROM THE READER SIDE*: the =Split= reader already contains a
redundant constraint today. A leaf spanning exactly one limb comes back as
that limb's OWN wire (=take= splits only where it must), so
=constrain_canonical= re-constrains a wire the buffer's =constrain_input=
already did. On that path the pass is a saving as well as a discharge, which
is why the reader's tests hold the pass constant and vary only the
constructor.

** WHY NO SHIPPED ARTIFACT FLIPS THE FLAG — and a correction to §1

Default OFF everywhere, and the gate was the usual one: 162 circuits
byte-identical, 5 identical modulo numbering (inherited from §9), 0 changed.

Better than that, MEASURED: scanning all 863 =.zkir= files in the repo — our
167 dumps AND every compactc fixture artifact — for a range constraint implied
by an earlier one on the same wire finds *ZERO*. So enabling the flag on
everything we ship today would remove nothing at all.

Two consequences, and the second corrects this note:

1. The flag is not a latent behaviour change waiting to be tripped. It does
   something only once a gadget starts constraining its own inputs, which is
   exactly the API this pass exists to permit.
2. *§1's table says the pass DIVERGES from compactc "which re-emits". No
   compactc artifact we hold re-emits.* The divergence is therefore
   PROSPECTIVE, not observed — which is a weaker case for the pass than §2(iii)
   made, and a weaker case against it too. It stays opt-in regardless: the
   claim would have to hold for artifacts we have not seen, and a differential
   against a re-emitting compactc would need the SAME normalisation run on
   both sides (as §8's four differentials already do for the fold) before it
   could be turned on by default.

*DEFERRED, with its own gate*: turning it on for the M10 lineage. Nothing
argues for it yet — the measurement above says it would move zero

snapshot plus that lineage's divergence ledger, not this note.

* 12. THE ALWAYS-TRUE ASSERT, as built (2026-09-06)

=minocrab_ir::v3::passes::drop_true_asserts=, run by =Builder3::finish= on
every circuit: an =Assert= whose operand is the IMMEDIATE 1 is deleted,
because it passes on every preimage. Nothing else is touched.

The case for it is §0's criterion rather than rows. notes/evm-calls.org §3.2
puts an outcome predicate behind =EvmCall::Outcome=, and for
=OutcomeRule = Always= that predicate is the constant =true=: =complete=
asserts it, the author cannot skip the check, and the assert must cost
nothing. dmd's call (2026-09-05) was to get that zero from a GENERAL fold
rather than a =CAN_FAIL= const branching the API — /"I'm inclined to just use
the fold, because it's a fairly small number of rows either way"/ — so the
API stays one shape and every constant-true assert in the tree gets the same
treatment for free. The effect layer already treats an immediate-1 GUARD as
no guard (=effects.rs=, =effect_guard=); this is the one residue that
survived it.

** FOLD FIRST, THEN DROP, THEN (optionally) DEDUP

=finish= now runs three passes in that order, and the new one's position is
forced by the same kind of argument as §11's:

- =c.assert(c.constant(1u64))= emits =copy %k = 1; assert %k=. Only the copy
  fold turns that into =assert 1=, which is the shape this rule deletes.
  Run BEFORE the fold it would see nothing at all. =assert_of_a_named_one_
  folds_then_drops_to_nothing= pins the pair: through =finish= the two
  instructions become ZERO.
- Against the dedup the order is free in both directions — the dedup only
  ever removes range constraints, which this rule never looks at, and this
  rule only ever removes asserts, which the dedup never looks at. It is
  placed between them because that is the order =finish= reads in.

ALWAYS ON, like the fold and unlike the dedup. It can be: the deletion is an
equality of the evaluation semantics, not a divergence from compactc that
needs a warrant (below).

** WHAT IT REFUSES TO DO, and this is the whole safety argument

An =Assert= on an immediate that is NOT 1 is an ALWAYS-FAILING circuit, and
it is left exactly as it is. Under the ZKIR semantics =assert= resolves its
operand as a boolean (=ir_vm.rs=, =resolve_operand_bool=): 0 rejects with
"Failed direct assertion", anything else with "Expected boolean". Deleting
one would turn a circuit the verifier REJECTS into one it ACCEPTS — the
unsound direction, and the only direction that matters here. The pass moves
in the other one: it removes a check that already held on every preimage, so
the accepted set is unchanged.

It also does no dataflow. A WIRE that happens to hold 1 is not this pass's
business; only =fold_immediate_copies= may turn such a name into an
immediate, and then only where it can prove the copy is a rename.

** THE LEAN THEOREM, and it is the STRONGEST of the three

=crates/minocrab-ir/lean/MinocrabProofs/AssertIr.lean=, cited from
=DROP_TRUE_ASSERTS_PROOF= via =lean_proof!= exactly as the other two are, so
=run_pipeline_verified= accepts the pass and =missing_theorems= catches a
rename. =lake build= green in both lean packages.

Where =FoldIr= and =DedupIr= can only preserve an ABSTRACTION of meaning —
=observe= for the fold (which renames wires), =streamBound= for the dedup
(which removes constraints) — this rule preserves =run= ITSELF:

#+begin_src lean
theorem dropTrueAsserts_preserves_run (M : Model C) (prog : Program) (π : Preimage) :
    Eval.run M (dropped prog) π = Eval.run M prog π
#+end_src

an equality of =MinocrabZkir.Eval.run= — memory, =pis=, =piSkips=, =outputs=,
and accept-vs-reject WITH its message — for every model, every carrier
assignment and every preimage. It rests on one step lemma
(=step_of_isTrueAssert=: the deleted instruction steps to =pure st=, because
=resolve= sends =.imm v= to =Fr.ofInt v= and =resolveBool= sends 1 to =true=)
lifted through the =foldlM= over the instruction list. That is why the pass
can be on for every shipped circuit without a §1-style warrant: there is no
divergence to warrant, only an instruction that did nothing.

Four theorems stand beside it, mirroring the other two files:
=dropTrueAsserts_sublist= (the output is a subsequence — nothing added,
reordered or rewritten), =dropTrueAsserts_passthrough= (everything that is not
a true assert survives with multiplicity and in order),
=dropTrueAsserts_keeps_failing_asserts= (the unsound direction closed a second
time, syntactically: an assert on any OTHER immediate is kept with
multiplicity), and =dropTrueAsserts_idem=.

The trigger is stated as =Fr.ofInt v = 1= rather than =v = 1=: the Rust
operand holds an already-reduced =Fr= where the Lean syntax holds the file's
signed literal, so the field reading is the faithful transcription.

** RUNG 3, EXECUTABLE: =MinocrabZkir/Smoke.lean=

Four =#guard=s beside the theorem, on the hand-traced program that file
already carries: prefixing =assert (imm 1)= leaves =pis=, the skip list and
the verdict identical to the run without it, while =imm 0=, =imm 2= and
=imm -1= each REJECT. The theorem is the general claim; these are the
witnesses that the two immediates really do fall on opposite sides.

** ZERO MOVEMENT, MEASURED — the rule is DORMANT today (SUPERSEDED 2026-10-10, §13: it fires on the =Pending= settles)

That is not luck, it is the same measurement said forward: scanning every v3

** =folded= DOES NOT GET IT, deliberately

=passes::folded= is the normaliser the instruction-for-instruction
differentials run over compactc's artifact AND ours (§8). It stays the COPY
FOLD ONLY. The rule deletes an instruction rather than renaming one, no
compactc artifact we hold carries its shape (measured above), and adding it
there could only ever hide a divergence: a compactc artifact that DID emit
=assert 1= is something we want a differential to say out loud, not something
to normalise away. The differentials' criterion therefore stays exactly what
§8 made it — "identical instruction for instruction, MODULO the naming of
constants" — and is not widened by this pass.

** THE INDEX CAVEAT, inherited and not widened

=AssertMessage.instruction= and =Region='s =[start, end)= are recorded at
BUILD time (=minocrab::v3=), so any pass that removes an instruction shifts
the positions after it. Pre-existing since §8 and restated in §11; this rule
inherits it and does not make it worse. The one thing it could have added — a
message stranded on a DELETED assert — is not a new failure mode either: the
deleted assert is the one that can never fail, so its message could never
have been printed. FIXED 2026-10-10, §13 — and the "never printed" half was
too generous: the stranded message did not vanish, it shifted onto whatever
instruction took its index.

* 13. BUILD-TIME INDICES, carried across the passes (2026-10-10)

The caveat §11 and §12 recorded (pre-existing since §8's fold) was a live
bug, not a theoretical one. =Circuit3= records two kinds of instruction
index while it builds — =AssertMessage.instruction= (=v3/effects.rs=,
=emit_assert=) and =Region='s =[start, end)= (=Circuit3::region=) — as

instructions: the copy fold on every circuit, the true-assert rule, and the
dedup where the opt profile turns it on. Every index after a deleted
instruction ran ahead of =Compiled3::ir=, so =Compiled3::assert_message(at)=
— which =minocrab_sim::v3::simulate_compiled= uses to name a failed check —

** THE MEASUREMENT, on the 214 workspace circuits before the fix

** THE FIX: every pass in =finish= is a filter, and says so in one place

Every pass =Builder3::finish= runs is a FILTER — its output is a
subsequence of its input, in order, with operands rewritten at most (the
Lean models prove it of the algorithms: =dedup_sublist=,
=dropTrueAsserts_sublist=, =fold_is_filter_map=) — so one kept-or-dropped
bit per input instruction determines where everything went. The rule is
ENFORCED, not just stated: all three passes delete through one helper,
=passes::retain_kept=, which runs the pass's keep decision under
=Vec::retain_mut= (each instruction once, in order) and records that same
return value as the instruction's bit. The pass cannot drop an instruction
without the map saying so, and cannot insert or reorder at all. The
=_kept= passes return a =Kept= beside the stream; the unsuffixed passes are
them with the map dropped. =Builder3::finish_kept= composes the maps in pass
order (=Kept::compose=), asserts that the result starts at the built
stream's length and ends at the finished one's (a pass added to =finish=
without composing its map fails there), and under =debug_assertions=
re-checks the law against both streams (=passes::check_kept=: each kept
instruction is the finished instruction at its position, operands included,
modulo the fold's variable-to-immediate rewrite; each dropped one is of a
kind some pass deletes). =finish= is its stream. The =Pass= trait's docs
state the filter rule for any pass that would join =finish=.

=Kept= stores the running count of survivors, =before[i]= = how many of the
first =i= instructions were kept, which gives the two maps the frontend
needs:

- =position(i)= — where instruction =i= landed, or =None= if it was
  deleted. =Circuit3::finish= moves each =AssertMessage= by it and DROPS the
  message whose assert was deleted (only the true-assert rule deletes an
  =assert=, and that assert cannot fail).
- =boundary(i)= — where the boundary in front of =i= landed. A region's
  =[start, end)= maps to =[boundary(start), boundary(end))=, which holds
  exactly the region's survivors in order, is empty when none survived, and
  keeps nesting because =boundary= is monotone.

=Circuit3::finish= then checks, under =debug_assertions= and without going
through =boundary=, that each surviving message sits on its own assert's
finished position in build order and that each region is exactly the run of
positions its surviving instructions landed on. Every circuit any test
builds runs both debug checks, so all 214 workspace circuits re-prove the
mapping on every =cargo test=.

Why this and not reconstruction after the fact: matching the finished
stream back against the built one is easy for the passes that rewrite
nothing and needs an argument for the fold, which rewrites operands; the
bit recorded as the decision needs none. And why not record indices late:
the regions and messages are taken where the author writes them, which is
before any pass can run.

** The API, and two panics for dmd

=Kept= is INTERNAL TIER: it lives in the private =passes::kept= module and
is re-exported from =passes= only under =unstable=, beside
=Builder3::finish_kept=, its one producer. It bakes in "every pass in
=finish= is a filter", which is a fact about today's =finish= and not a
promise for the semver tier (notes/library-api.org §1). The =_kept= passes,
=retain_kept=, =Kept::identity= and =Kept::compose= are crate-private;
=compose='s length check is an internal invariant of =finish_kept=.

Two rejections on the unstable surface are build-time panics, because the
bound is a stream length known only at run time (the ladder's last rung):
=Kept::position(i)= panics for =i >= input_len()= and =Kept::boundary(i)=
for =i > input_len()=, each with a message naming the stream's length and
saying to take the index from the same =Builder3= before =finish=. They
exist so that =None= from =position= means "deleted" and nothing else: an
index from the wrong builder would otherwise drop a message or clamp a
region silently, the bug class this section fixes. RECORDED FOR DMD.

** Proof and model status

The pass BODIES changed shape: the fold and the dedup now decide inside a
=retain_kept= closure instead of pushing onto a fresh vector, and
=drop_true_asserts= is a =retain_kept= over =!is_true_assert=. Signatures
and outputs did not change (the =_kept= passes equal the unsuffixed ones on
100,000 random streams, =passes/kept.rs=). The Lean correspondence covers
the algorithm as transcribed and rests on review that the Rust implements
it; the new bodies were re-read against =FoldIr.lean=, =AssertIr.lean= and
=DedupIr.lean= and are the same algorithm. The Kani stream harnesses are
the non-closing specimens they were. The metadata remap itself — =Kept=,
its composition, =Circuit3::finish='s moves — is NOT covered by any proof:
it is tested (fixed and random streams per pass, random =Circuit3=
programs, the debug checks on every built circuit), with the Lean
=*_sublist= theorems as the warrant for the one property it depends on.

** What else holds a build-time index, checked

- =Disclosure3= holds NAMES (=DisclosedWire::Named=) or the folded constant
  (=DisclosedWire::Constant=), never an index — unaffected, by §8's design.
- =Circuit3::instruction_count= / =Builder3::len= are read DURING the build
  (the entry core's "declaration emitted nothing" check, the disclose
  tests' "costs no instruction"), where build-time is the right time — with
  one exception that indexed the FINISHED stream: =minocrab-sim='s
  =cryptocost= example sliced =est_rows(&compiled.ir)[before..]= with a
  build-time =instruction_count()=. It was right only because the six
  frame instructions in front of the ECDSA verify survive every pass. It
  now measures the verify as a region of the finished stream; its output is
  byte-identical.
- The deferred hooks (=Circuit3::then=) hold lowered ops and a guard =Val=,
  and are emitted before =finish= runs its passes.
- =minocrab_sim::v3::profile= and =name_the_failed_assert= consume
  =Compiled3::regions= / =assert_messages= — fixed through them, no change of
  their own. =minocrab-bench='s =write_profiles= runs =profile()= on the
  eDSL =Compiled3= of every benchmark circuit (compactc's parsed =.zkir=
  carries no regions), so =target/bench/profiles/= is fixed through it too
  and differs from any earlier run.
- =passes::run_pipeline= and the CLI run over a bare instruction stream with
  no metadata beside it, so there is nothing for them to move.

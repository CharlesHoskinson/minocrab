  pinned at a finalized hash; checks the deployed verifier key's hash

  facade needs the INDEXER (dust UTXOs are derived by replaying ledger

  =state_conflict=, =ambiguous_submit=; duplicates declared acceptable).

Its own justification (=intent.ts= header): "the one step that cannot
move to Rust: the compiled contract's bindings and executor are
JavaScript." That is the claim this repo makes false.

Proving is a plain async Rust function. zkir-v3, transient-crypto and
base-crypto never touch =std::process=; parallelism is rayon threads in
the caller's process. Midnight's "proof server" is an HTTP wrapper
(=proof-server= crate, tokio worker pool) around the same function,
for JS/browser clients. The one external touch is the KZG params
(=MidnightDataProvider=: fetched from =srs.midnight.network= on first
use, SHA-256 checked against compiled-in hashes, cached at =$MIDNIGHT_PP=
/ =$XDG_CACHE_HOME/midnight/zk-params= / =~/.cache/midnight/zk-params=;
=MIDNIGHT_PARAM_SOURCE= overrides the host). Ship the params in the
image and no network access is needed.

* 3. Using the minocrab ZKIR with the sidecar UNCHANGED

Possible, and it is the tested combination. The sidecar never
interprets the IR: compactc's JS executor produces args + transcript,
the ledger's =construct_proof= (=ledger/src/construct.rs:515-573=)
turns them into the =ProofPreimage= (=inputs= = field vec of the
arguments, empty =private_transcript= for a witness-free circuit,
=public_transcript_inputs= = op field_repr, comm_comm from the
prototype's randomness, =binding_input= 0), and whatever IR sits at
=zkir/<circuit>.bzkir= proves it. Call-compatibility (ledger-abi.org §6:
same preimage → identical =pis= and =pi_skips= on both IRs,
=IrSource::check= accepts both, tamper twins reject) is exactly "our IR
accepts the executor's preimage".

Changes, none in the mpc repo:
1. Artifacts: =minocrab_zkir::v3::write_zkir= → =.zkir= JSON in compactc's
   on-disk form → the pinned =zkir-v3= binary (the flake's, the same
   tool compactc invokes; =compile-many= does keygen) → =.bzkir= +
   prover/verifier keys.
2. =@sig-net/midnight-contract= ships them under =keys/= and =zkir/=
   with the circuit names; regenerate =expectedVk=.
3. Deploy tooling reads the verifier keys from the same managed dir, so
   a fresh deployment picks them up. Nothing to migrate.

* 5. Trust: a stateless, untrusted DA layer

The MPC keeps no Midnight state; everything comes from an RPC endpoint
it does not verify. =indexer.rs:120-132= gathers a =BlockProofSeed=
(header, body, system events) and =drop()=s it: "no verifier or
persistence policy yet".
1. READER is the exposure: a lying endpoint can fabricate a
   signBidirectional request and the MPC signs an attacker-chosen EVM
   tx. Independent of TS vs Rust. Fix: verify the seed (extrinsics root
   vs header, header vs finality) or quorum over endpoints.
2. Publisher reads fail safe for respond: transcript independent of
   contract state; a lie yields a rejected tx or a vk mismatch (keep
   the =expectedVk= gate). A lie about ledger parameters skews the fee,
   bounded by the wallet balance.
3. A Rust DUST wallet replayed from untrusted events: no theft without
   the key; phantom UTXOs → repeated invalid submits, hidden UTXOs →
   stall, stale Merkle root → spend fails. Persisted state must be
   rebuildable from genesis. The funding seed is a hot key either way.
4. Submission: silent drops, "invalid" after inclusion → retries;
   duplicates are by design acceptable; stranded DUST on the 5-min
   recipe TTL is the cost.
5. Version drift between the pinned ledger crate and the live network
   → silent rejections. Both repos are on rc tags.
The port removes the proof server as a network dependency and stops
executing an npm package's JS as trusted code on the signing path.

** The exact =zkir-v3= invocation

Confirmed by running =zkir-v3 --help= in the devshell: four
subcommands (=mock-compile=, =mock-compile-many=, =compile=,
=compile-many=), matching the note's guess. The pipeline:

1. =minocrab_zkir::v3::write_zkir= writes =<out>/zkir/<circuit>.zkir=
   for each of the three circuits (compactc's on-disk JSON form).
2. =zkir-v3 compile-many <out>/zkir <out>/keys= (confirmed CLI:
   =compile-many <IR_DIR> <KEY_DIR>=). Reading the binary's own source
   (=~/.cargo/git/checkouts/midnight-ledger-*/04c9c5d/zkir-v3/src/
   main.rs=) matters here: =compile-many= does keygen (writes
   =<KEY_DIR>/<circuit>.{prover,verifier}=) but, EXACTLY LIKE
   =compactc=, also writes each circuit's =.bzkir= AS A SIDE EFFECT of
   loading a bare =.zkir=, INTO THE SAME =IR_DIR= the =.zkir= came
   from (=main.rs='s =maybe_bzkir=: on a =.zkir= extension it loads
   the =IrSource= and =tagged_serialize=s a =.bzkir= sibling before
   returning). So there is no separate "make me a =.bzkir=" step —
   =<out>/zkir/<circuit>.bzkir= appears next to the =.zkir= once
   =compile-many= runs, matching the managed layout named in
   milestones.org M29 A without any extra copying in this crate.

Located via =$ZKIR_V3= else =zkir-v3= on =PATH= (a bare name with no
=/= makes =std::process::Command= search =PATH= itself — no =which=
dependency needed).

** The hash function: provenance and the pin

=hashVerifierKey= lives at
=@midnight-ntwrk/compact-js/dist/cjs/ContractKeyLocation.js= (checked

@midnight-ntwrk/compact-js=, version 2.5.5-rc.7), lines 18-20:

function hashVerifierKey(bytes) {
    return (0, node_crypto_1.createHash)('sha256').update(bytes).digest('hex');

#+end_src

=sig-net/mpc='s =chain-signatures/midnight-publisher-ts/src/prover.

** C. The construction gate — the ledger's preimage, not a hand-built one

*** What was wrong with the old differential

=tests/signet_contract_differential.rs= built its =ProofPreimage= by hand:
=inputs= a =Vec<Fr>= the test wrote out, =public_transcript_inputs= an
=op.field_repr= over ops the test wrote out, =communications_commitment= a
=transient_commit(&inputs, rand)= the test computed. Every one of those is
a SECOND READING of a rule =ledger/src/construct.rs= already states, and a
differential run against a second reading tells you nothing about the
first. Two artifacts agreeing on a preimage neither of them will ever see
is not evidence.

*** What replaced it

=crates/minocrab-contracts/tests/support/signet_call.rs= — the one place
in the suite that builds a singleton preimage, through the production
path:

#+begin_example
Impact program ──partition_transcripts──▶ Transcript (gas, effects, version)
                                                 │
arguments as an AlignedValue ────────────────────┤
                                                 ▼
                                      ContractCallPrototype
                                                 │
            Intent::new ──▶ add_call ──▶ communication_commitment
                                         ContractCallExt::construct_proof
                                         (construct.rs:515-573)
                                                 ▼
                                          ProofPreimage
#+end_example

The preimage is READ BACK OUT of the =ContractCall= the intent carries,
not reconstructed from what =construct_proof= would have said — so the
bytes under test are the bytes a real intent holds. §3's claim ("the
sidecar never interprets the IR; =construct_proof= makes the preimage and
whatever sits at =zkir/<circuit>.bzkir= proves it") is now the code path
the tests take, not a description of one.

=tests/signet_construction.rs= replaces the old file: the same
call-compatibility gate on all three circuits (=assert_call_compatible= —
same input/output schema, same =pis= and =pi_skips= under our simulator,
=IrSource::check= accepting on both sides) and the same three tamper twins
(tampered event byte, tampered signature byte, swapped event name), all on
that preimage. =partition_transcripts= is content-blind — it runs whatever
program it is handed — so the tampers survive the move onto the production
path unchanged.

*** Three facts that were prose and are now assertions

1. =the_ledgers_inputs_are_the_arguments_field_repr=: =construct_proof=
   fills =inputs= from =ValueReprAlignedValue(call.input).field_vec()=,
   i.e. the argument value's =value_only_field_repr=. The hand-written
   limb lists the suite used before were right, and this says why.
2. =the_alignment_does_not_reach_the_preimage=: a typed =[Bytes<32>,
   Uint<8>, Bytes<128>]= argument value and a flat =[Field; n]= one over
   the same limbs give BYTE-IDENTICAL preimages (tagged-serialized and
   compared). The ledger reads an argument value only through its field
   repr; the alignment never enters the transaction.
3. =input_schema_matches_the_corpus_artifact=: the corpus artifacts
   declare 8 / 9 / 9 =Scalar<BLS12-381>= inputs, and the ledger-built
   preimages carry exactly that many — so the differential is comparing
   two circuits that read the same argument list, not two that happen to
   agree on a prefix.

*** The hand-built helper: REDUCED TO A WRAPPER, not deleted, and why

The milestone allowed either. =serialization/deployed.rs='s
=misc_preimage= survives as

#+begin_src rust
pub fn misc_preimage(inputs: Vec<Fr>, misc_bytes: &[u8]) -> ProofPreimage {
    call_preimage("respond", scalar_input(&inputs), misc_bytes)
}
#+end_src

because its caller is =serialization_conformance='s proptest over
thousands of generated payloads, which has raw limbs and no typed argument
value to hand. Fact 2 above is exactly the licence for that: the flat
alignment and the typed one produce the same bytes, so this wrapper is
not a second construction — there is now ONE definition of a singleton
preimage in the workspace, and this is a call to it. The
=signet_contract_differential.rs= copy was deleted outright.

=bench.sh= dumps its preimages from =--test signet_construction= now, so
BENCHMARK.md's singleton rows price the preimage production builds.

*** The gate

=tests/signet_ledger_apply.rs=, per respond circuit:

1. =ContractDeploy= a singleton whose three operations carry the COMMITTED
   managed verifier keys (§8's =managed/keys/*.verifier=) into a fresh
   =LedgerState=; =well_formed=; =apply=.
2. Decode the golden's singleton call through a mechanical translation of
   =chain-midnight/src/emissions.rs:96-148= — run the guaranteed
   transcript under the ledger VM on an empty =QueryContext=, take the one
   =VersionedLogItem=, check version 1 / type =Misc= / one =Bytes<288>=
   cell, split =name(32) ‖ payload(256)= — and pull the request id and
   signature OUT of that payload at the singleton's declared offsets.
3. Build OUR call on those same values through C's path, =well_formed= it
   against the deployed state, =apply= it.
4. Compare the emission the LEDGER RECORDED while applying ours (an
   =EventDetails::ContractLog= off =TransactionResult::Success=, not a
   re-run of our own program) with the golden's.

*** The comparison, field by field

COMPARED and required equal:
| field | why it must match |
| =ContractCall::entry_point= | the sidecar addresses the circuit by this name |
| the guaranteed transcript's Impact program, OP FOR OP | this is the emission: =Push= of =[Bytes<4> version, Bytes<1> tag, Bytes<288> data]=, then =Log= |
| =fallible_transcript= absent on both | mpc's reader REFUSES a singleton call that has one (=UnsupportedFallibleCall=) |

| the logged cell's alignment: one =Bytes<288>= atom | ditto |
| all 288 emitted bytes: =pad(32, name)= ‖ payload(256) | the name selects mpc's =EmissionKind=; the payload is what the MPC signs over |

NECESSARILY DIFFERENT:
| field | why |
| =ContractCall::address= | theirs is the capture chain's deployment =b116cd04…=; ours is a fresh =ContractDeploy= whose address derives from its own nonce and initial state. Unmatchable without replaying their deployment, which is impossible by construction — their operations carry compactc's verifier keys and ours carry MinoCrab's, and that difference IS the swap |
| =communication_commitment= | =transient_commit(input ‖ output, rand)= over a per-call =rand=; the sidecar sampled theirs, this suite pins ours so dumped preimages stay reproducible |
| =ContractCall::proof= | theirs a real =ProofVersioned::V3=; ours a =ProofPreimageVersioned::V2=. This gate runs under the proof-preimage marker, where =ProofKind::proof_verify= is a NO-OP — which is precisely why rung E exists |
| intent =binding_commitment= / =ttl=, tx =binding_randomness= / =network_id= | per transaction, per chain |
| =Transcript::gas= | see below |

The gas figure is the one measured surprise, and it is worth writing down.
Both sides declare =bytes_written= 678, =bytes_deleted= 678 and
=read_time= 0 (the singleton reads nothing). But the golden declares

partitioned by the sidecar against the capture chain's
=crate-ledger-9.1.0.0-rc.3= parameters, ours against =INITIAL_PARAMETERS=
at rev =04c9c5d=. Printed by the test, not asserted; our transaction

build → prove → BALANCE → sign → seal. Three of the four orderings are forced,
which is worth writing down because the sidecar's ordering looked arbitrary:

- balance after prove, because the fee depends on the transaction's own size
  and therefore on the proof sizes (=fees_with_impl= over the proven tx). The
  sidecar does the same thing — =prove= then =balanceUnboundTransaction=.
- sign after balance, because a dust REGISTRATION added by the wallet is signed
  by =Intent::sign='s third key list.
- seal last, by the type: =well_formed= only accepts a =PureGeneratorPedersen=
  binding, and sealing closes over each intent's contents.
- =sign= is generic over the proof kind, because =data_to_sign= erases proofs
  and signatures before hashing — so the signature does not depend on whether
  the transaction has been proved, and the cheap gate can exercise the same
  function the real one does.

All three of =FundingKeys='s lists are EMPTY for a respond intent today: it
carries no unshielded offer and no dust registration, so =Intent::sign= has
nothing to sign and the transaction's authority is its proof.

*** Proving

** C2: =Deployment= from =expectedVk.json=, checked against the keys

=ManagedDir::deployment(address, circuits)= used to build the table by
calling =self.verifier_key_hash(circuit)= for each circuit — i.e. by hashing
the =.verifier= files on disk. That table can never disagree with itself:
whatever the files say IS the table. Now it:

1. Reads and parses =<root>/expectedVk.json= (new: =ManagedDir::
   expected_vk_path=, a private =expected_vk_table= using =serde_json= —
   a new =[dependencies]= entry, the same shape =signet-artifacts= already
   writes the file with).
2. For each requested circuit, looks up the JSON's hash (missing ->
   =PublishError::UnknownCircuit=, same as before) and separately computes
   =self.verifier_key_hash(circuit)= from the =.verifier= file.
3. If they disagree: =PublishError::ExpectedVkOutOfSync { circuit,
   json_path, json_hash, file_hash }=, a NEW error variant (distinct from
   =VerifierKeyMismatch=, which compares against a DEPLOYED contract's
   operation, not the package's own files), with a message naming the
   circuit, the JSON path and BOTH hashes:
   #+begin_example
   respond: crates/signet-artifacts/managed/expectedVk.json records
   <json-hash>, but the verifier key on disk hashes to <file-hash> — the
   shipped expectedVk table and the shipped keys are out of sync (rebuild
   the managed directory)
   #+end_example
4. Only then builds the =Deployment= — from the JSON's hash, not a recompute
   — so what a publisher carries is the SHIPPED table, checked, not a
   table that is definitionally consistent with itself.

The gate: a new test, =a_corrupted_expected_vk_entry_is_caught_against_the_key_file=
(=tests/publish.rs=) — a temp copy of the committed managed directory's keys
and =expectedVk.json=, one hex character of RESPOND's JSON entry flipped
(still 64 well-formed hex, just wrong), asserts =deployment()= returns
=ExpectedVkOutOfSync= naming =respond=, the corrupted JSON hash and the real
file hash. =tests/real_proof.rs='s temp managed directory (built fresh by
local keygen, never touched by =signet-artifacts::generate=) did not carry
an =expectedVk.json= at all until this rung; it now writes one right after
writing the key files, hashing the same =vk_bytes= it just wrote — self-
consistent by construction, since that test's own point is proving under

** Future options for the proving step, not taken (dmd, 2026-09-24: "play it safe this time")
The singleton's proof binds nothing anyone relies on — readers verify the ECDSA signature themselves — so its cost is pure ledger plumbing, and three ways to cut it were costed after the M43 numbers came in. None was taken; recorded here so the next person does not re-derive them.

1. THE PAYLOAD AS THE ARGUMENT (the one to take first, when the contract next moves). Change the Compact source to =respond(payload: Bytes<256>)= and =respondBidirectional(payload: Bytes<256>)=, the circuit emitting the payload verbatim; the MPC serialises off chain. The argument's FAB limbs are then the logged cell's limbs, so the port has no re-limbing and no per-field constraints: a handful of equalities plus compactc's default range constraints on ~9 limbs, roughly 300 rows, k=9, about 0.05 s per proof against today's 0.10–0.18 s. Footprint: the Compact source and its simulator tests in midnight-integration; encoders =encodeSignatureRespondedEventPayload= / =encodeRespondBidirectionalEventPayload= in =@sig-net/midnight= beside the existing decoders (the layout defined once); ~10 lines in the sidecar's =intent.ts= (build one =Uint8Array= instead of the event struct, =CircuitArguments= becomes =[Uint8Array]=) and its test expectations; nothing in the Rust node, since the stdio protocol stays field-based; the interface crate regenerates again. Emitted bytes are identical, readers unaffected.
2. DROPPING THE RANGE CHECKS ON THOSE LIMBS (rejected for now). Sound for this contract as it stands: the arguments are witnesses, the public inputs are the transcript the ledger built from bytes, and the circuit would only assert witness limb = transcript limb, so an out-of-range witness can never satisfy it and the whole op sequence stays pinned regardless. Rejected because (a) it is a latent hazard the moment anything consumes the limbs in-circuit or a cross-contract caller trusts the communications commitment (the taint lint's whole reason to exist), (b) compactc always constrains arguments, so it would be the first singleton circuit that is NOT a port — the PI-equality gate, the constraint-prefix check and the interface agreement suite would all need a carve-out, and those gates are much of why the swap is reviewable, and (c) the win is under 300 rows, k=9 → maybe k=8, tens of milliseconds. If ever taken: MinoCrab side only, with the exemption written in the circuit and the taint baseline.
3. BATCHING (deferred: "too tricky now"). A =respondMany(payloads: Vector<N, Bytes<256>>)= emits N events under ONE proof: prover time per post ÷ N, and — the only lever that moves the on-chain fee — one proof verification instead of N, since verification is the fixed compute term in the fee. The cap is the guaranteed-section budget of the fallibility model (notes: =INITIAL_LIMITS=, ~15 ms + 2 µs/byte per call, over-budget calls demoted whole): the measured transcript is ~1.3 ms per event plus verification, so N is small (two to four, to be measured with the partitioner before choosing), and the sidecar would hold posts to fill a batch, a latency trade the current one-post-per-intent protocol does not make.

Zero proofs is not an option: the ledger refuses an operation with no verifier key (=VerifierKeyNotSet= in =verify.rs=) and every call carries a proof against its operation.

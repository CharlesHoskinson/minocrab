#+title: M23 R3 — the taint lint: design, warrants, findings, and the ruling

The instrument api-safety-survey §B3 asked for: a static pass proving every
byte-atom hash-preimage limb bounded to its own byte width or constant — the
class no test on honest preimages can see, because an honest prover always
supplies in-range values. Built 2026-08-27.

* 1. Where it lives and how it runs

- =minocrab_ir::v3::taint::audit(&[Instruction]) -> Vec<Finding>= — pure
  function of one circuit's stream, ~150 lines of analysis plus the exact
  interval arithmetic below. In =minocrab-ir= because that is where the pass
  layer lives and where M23 R4's Kani harnesses will point
  (=cargo kani -p minocrab-ir=).
- The gate: =crates/minocrab-contracts/tests/taint_lint.rs= over
  =support::circuits()= — all 200 workspace circuits and every future one,
  since the snapshot registry is the one list a new circuit must join.
- The corpus side-instrument (not a gate):
  =cargo run -p minocrab-ir --example taint_corpus= audits every v3 corpus
  artifact, i.e. compactc's own output, with the same rules.

* 2. The subject, per the scoping spike

=Keccak256= and =PersistentHash= — the two instructions carrying an
=alignment= and absorbing byte atoms. =TransientHash= (and =HashToCurve=)
absorb native field elements: no byte atoms, no injective-packing concern,
deliberately out of scope (noted in the code).

* 3. What the chip already enforces — the premise correction

The spike framed the check as "each limb feeding the hash must be
constrained to its own byte width". The in-circuit decoder turns out to
enforce exactly that ITSELF: =fab_decode_to_bytes_atom= (zkir-v3
ir_vm.rs:125-175) decomposes every =bytes= limb with
=assigned_to_le_bytes(f, Some(width))=, which midnight-circuits documents as
UNSATISFIABLE when =f= exceeds =width= bytes (decomposition.rs, "Unsatisfiable
Circuit"). So the digest always binds the LIMB.

What nothing enforces is one level up: a limb PACKED from several narrower
segments (=a + b·2^8k=) is injective in those segments only if each segment
is bounded to its own slot — §B3's precondition. The lint therefore demands a
/derivable/ bound on the limb wire, and its bound propagation only succeeds
when every wire feeding the packing arithmetic is itself
constrained-or-constant. That is the §B3 check, mechanized.

Honest boundary, stated in the module docs: the lint proves BOUNDS, not
shift-layout disjointness. Overlapping segment shifts are the serializer's
own layout invariant, pinned by its byte-equality tests, not by this lint.

* 4. The marking rules, each with its cited in-circuit warrant

Direction of caution: under-marking is safe (over-fires → a human looks);
over-marking is the danger (false negative). When unsure, do not mark.

Position-independent (ZKIR v3 is SSA — push-only upstream memory, fresh
identifiers in =Builder3= — so a constraint anywhere bounds the wire
everywhere, the =dedup_range_constraints= argument):
- =ConstrainBits{bits}= → =2^bits−1=; =ConstrainToBoolean= → 1 bit.
- =ReconstituteField= asserts BOTH its operands in-circuit
  (=assert_lower_than_fixed=, ir_vm): divisor < =2^(255−bits)=, modulus <
  =2^bits=.
- =Bytes32FromLowHigh= asserts low < =2^248= (32nd byte zero) and
  byte-checks high.

Forward-propagated producers:
- =DivModPowerOfTwo=: canonical full decomposition
  (=assigned_to_le_bits(.., true)=) — mod < =2^bits=; div = val ≫ bits, so
  any bound on val shifts down (val canonical ≤ p−1).
- =Encode= of a KNOWN-=Bytes32= input → (low ≤ =2^248−1=, high ≤ 255),
  recomposed from already-range-checked assigned bytes
  (ir_instructions/encode.rs:93-96). Bytes32-ness is tracked through the
  producers (=IntoBytes32=, =ReverseBytes=, the hashes,
  =Bytes32FromLowHigh=, typed inputs); a 2-output =Encode= of unknown type
  is NOT marked — it could be JubjubPoint coordinates, field-wide.
- =Bytes32IntoLowHigh= → (248, 8), same recomposition warrant.
- =Copy= inherits; =CondSelect= takes the max of both branches (the bit is
  converted to an =AssignedBit=, so the output IS one of them).
- =Add=/=Mul=: exact interval arithmetic, valid only while the result cannot
  wrap: a ≤ Ma, b ≤ Mb ⇒ a+b ≤ Ma+Mb, a·b ≤ Ma·Mb over the integers iff the
  result ≤ p−1; anything larger is dropped as unbounded.
- =TestEq=/=Not=/=LessThan= outputs are converted bits → 1.
- Explicitly NOT marked: =PublicInput=/=PrivateInput= outputs (the witnessed
  VALUE is free; only its shape is typed — the instruction's own doc), =Neg=
  (wraps), =FromBytes32= (a full reduction), and every curve op.

WHY EXACT MAXIMA rather than bit counts: the motivating packing
=a + b·2^64= with both segments ≤ =2^64−1= is EXACTLY ≤ =2^128−1= — a
16-byte atom. Any =max(n,m)+1=-bits rule reports 129 and falsely fires on
every full-width packing. =Max= is a 4×u64 exact upper bound with checked
add/mul/shr; a one-bit overlap (=b·2^63=) correctly exceeds 128 bits.
Pinned by the =max_arithmetic_is_exact= unit test; this arithmetic is also
the natural first Kani target for R4.

The operand↔atom mapping follows the decoder's own consumption rule, not
=minocrab_ledger::atom_limbs=: a =bytes n= atom consumes its leftover
(most-significant, =n mod 31=-byte) limb FIRST, then =n/31= full 31-byte
limbs — and =bytes 0= consumes NOTHING (the decoder's =chunks + (stray!=0)=
is zero), where the Impact FAB rule floors at one limb. Option and compress
segments are reported as unmappable: the in-circuit decoder REJECTS both,
so they cannot occur in a proving circuit.

* 5. The findings — 329, frozen, classified, awaiting dmd

First run over all 200 circuits: 329 findings across the vault's four forks
(59+49+49+49), manager (90), kernel_tokens (19), xcall_with_payment (8),
mint_tokens (4), xcontract_events (+borsh) (2). Frozen byte-for-byte in
=tests/taint_baseline.txt=; the gate fails on any NEW finding (and on a
resolved one, so progress is recorded). Per the R3 spec no allowlist entry
is written without dmd's ruling — the baseline is the freeze that keeps the
instrument live meanwhile, and this section is the write-up that goes to
dmd.

** The headline negative: ZERO free-witness findings

No finding names a =%w.*= wire (=private_input=). Every prover-controlled
limb that reaches a byte-atom hash is constrained in-circuit, in all 200
circuits. The sharpest §B3 shape — a free witness whose digest binds
nothing — does not occur.

** Class 1 (317): public-transcript wires, the ledger's warrant

Every one roots in a =%pi.*= wire — =public_input=, i.e. the popeq ledger
reads and cross-contract results — either directly (261) or through
=sel=/=add=/=div= wires derived from them (56). In-circuit these are free
witnesses; what binds them is the =Impact= instruction pushing
=select(guard, x, 0)= into the public-input stream, which the verifier
checks against the actual transcript — and the ledger only ever produces
transcripts whose stored values are normalized in-range. So the warrant is
REAL but EXTERNAL: it is the ledger's invariant, not a circuit constraint.

Platform parity, measured: compactc's own artifacts have the identical
property — 27 of the 84 v3 corpus artifacts fire, 195 findings, same class
(=%contractAddress=, =%value=, =%sender=, =%requestNonce= …). The survey
already said "compactc's byte-wise form has the same property"; now it is a
number.

The wrinkle that makes this dmd's call rather than a mechanical extension:
GUARDED reads. When the guard is false the Impact pushes zeros and the wire
is genuinely FREE — whether a hash over it matters then is contract-level
reasoning (the vault's guarded branches discard the result, but the lint
cannot know that). A sound "Impact-bound" marking rule would have to parse
popeq shapes out of Impact element streams and handle the guarded case
conservatively.

** Class 2 (12): proven, but wider than the slot

=erc20_vault{,_opt,_borsh,_modern}::{deposit,approve_router,swap}= — the
M7 pass-1 ABI-word construction feeds a =%div.*= wire proven ≤ 103 bits
into the 1-byte hi limb of a =bytes<32>= word. Here the chip's own
=assigned_to_le_bytes(f, Some(1))= is what enforces the slot (§3): an
out-of-range value is unsatisfiable, honest values fit by construction, and
the wire is derived by constrained arithmetic, not witnessed. A precision
gap of the lint (it cannot see that the algebraic shift arrangement keeps
the top byte small), not an injectivity hole.

** The options for dmd, ranked as the R3 spec ranks them

1. Extend the taint rules with the Impact/popeq warrant for UNGUARDED reads
   (guarded ones keep firing) — closes most of class 1 mechanically, with
   the parsing cost above.
2. Extend with a "chip-enforced at absorption" rule — since the decoder
   range-checks every limb it absorbs (§3), the residual value of the lint
   is packed-segment discipline; this would close class 2 and arguably all
   of class 1 too, at the cost of no longer flagging wires whose only bound
   is the absorption itself.
3. Keep the frozen baseline as-is: the instrument audits all new code;
   the recorded classes stand as documentation.

THE RULING (dmd, 2026-08-28): option 1 — "less noise is better, but let's
be clear about the limitations of the lint in the current form." Option 2
explicitly not taken (it would trade away the wires whose only bound is
the absorption). The limitations statement is now a named section of the
module docs; §7 below is the as-built.

* 7. As built — the option-1 extension (2026-08-28)

THE RULE (=mark_popeq= in taint.rs, wired into pass A): an =Impact= whose
guard is an IMMEDIATE NON-ZERO and whose element stream parses EXACTLY as
=popeq=/=popeqc= — =[0x0c|0x0d, atom count, one header element per atom,
the limbs]= (=Op::field_repr= ops.rs:477-480, header fab.rs:596-608) —
bounds each embedded wire to its limb's byte width, per the FAB limbing
(stray-first =n mod 31= MSB bytes then 31-byte chunks; =bytes<0>= is one
zero limb). Anything that does not parse cleanly marks NOTHING
(under-marking is the safe direction). A VARIABLE guard — even one that
is in fact always 1 — marks nothing: when the guard is false the Impact
pushes =select(guard, x, 0) = 0=, the transcript comparison passes on
zero, and the wire is genuinely free. That is the ruling's "guarded reads
keep firing" half, enforced syntactically.

THE WARRANT'S HONEST STATUS, restated in the module's new "Limitations,
stated plainly" section: this is the lint's ONE external rule — every
other marking cites an in-circuit constraint; this one runs through the
verifier's transcript equality plus the ledger's normalization invariant
(=process_read=). A clean run now reads "every hash-preimage limb is
bounded in-circuit, or is an unconditional ledger read the platform
binds." Also stated there: popeq ONLY (write/=idx=-key embeds carry a
different argument — transaction well-formedness — deliberately not
encoded), and guard recognition is syntactic.

THE NUMBERS: baseline 329 → 101, zero new findings. Every survivor

Class 2 (the 12 ABI-word =div= shifts) RESOLVED ITSELF: with real bounds

THE QUESTION PUT TO THE RULE: does the ledger-read warrant extend to a guarded read — "a popeq'd value is the on-chain cell of that FAB alignment hence in range, and a SKIPPED guarded read yields 0, which is also in range"? IT DOES NOT, and the second half is the error. The two in-circuit facts:

- A =public_input= IGNORES its guard in-circuit. The synthesis arm is =I::PublicInput { guard: _, val_t, output }= (zkir-v3 =ir_vm.rs:978-1004=, pinned at rev =04c9c5d=): it resolves the wire straight out of the preprocessed witness memory and =assign_incircuit='s it, with no constraint for a =Scalar<BLS12-381>=. So =public_input … guard: %g= is EXACTLY as free a witness as an unguarded one; the guard is metadata for the transcript walk, not a constraint.
- The Impact pushes =select(guard, x, 0)= (=ir_vm.rs:869-882=). With =%g = 0= the pushed public input is 0 for ANY =x=, the verifier's transcript comparison passes on the zero, and the wire is unbound. That is precisely the sentence the M23 R3 ruling already carries ("guarded reads keep firing"), now met in five circuits instead of one.

Where "a skipped read yields 0" comes from, and why it is not a warrant: it is the OFF-circuit semantics — upstream's =run= pushes zeros and records =pi_skips= for a guarded-off Impact (=ir_vm.rs:507-520=), and the guarded-off =public_input= yields =default_ir_value(val_t)= and consumes no transcript (our mirror, =minocrab-sim/src/v3.rs=, the =I::PublicInput= arm, commented "ir_vm.rs:348-366 — a guarded-off read yields the type's default and consumes nothing"). That run IS THE WITNESS GENERATOR. An honest prover's witness holds 0 there; a malicious prover's holds whatever it likes. Reading it as a bound would be exactly the category error §4's "soundness direction" warns against, and it would be an OVER-marking — the one direction that produces false negatives. So: no rule extension. Pinned instead by =a_guarded_read_under_a_guarded_popeq_stays_free= in =taint.rs=, which builds the real shape (guarded =public_input= + guarded popeq → still fires; the same guarded gate under an UNCONDITIONAL popeq → clean), plus a new "Limitations, stated plainly" bullet, so no future change can flip this quietly.

THE ARGUMENT THAT WOULD DISCHARGE CLASS A, stated for dmd rather than written: OBSERVABILITY, not bounds. When =%g = 0= every Impact that would publish the digest — the mint's coin-commitment push, the =tokenType= embed — is guarded by the SAME bit and also pushes zeros, so a forged preimage buys the prover nothing: the branch has no effect to steal. That is a real argument and it is what makes the vault sound. It is also a different proof obligation from the one this lint discharges: it needs a reachability/taint walk showing the digest reaches the transcript ONLY through Impacts guarded by =%g= and reaches no =Assert= at all, and a single unguarded consumer makes it wrong. Call it option 4 beside §5's three. Until dmd rules, class A stands as the ruling's own live class, now larger.

** Class B (1 new, 3 already frozen): =Uint::sub_with='s =add(a, neg(b))= — RULED, N1-N3 built (§9)

The new line is =erc20_vault::complete_swap= 211, =%add.98= into the =bytes<16>= value atom. The premise of "is the result range-checked in a way the lint recognises UNGUARDED, and why does the guarded form lose it?" turns out to be false: THE UNGUARDED FORM FIRES TOO, and has since the first run. =kernel_tokens::s_send_shielded= 61 / =%add.20= is the unguarded instance and is baseline line 5. The lint has never recognised =sub_with= at all, in either form, and the reason is structural rather than about guards: the lowering is =c.assert(ge(a, b)); let n = c.neg(b); from_field_unchecked(c.add(a, n))= (=minocrab-std/src/v3.rs=, =Uint::sub_with= / =BoundedUint::sub_with=; =from_field= became =from_field_unchecked= at =06d268e=), =Neg= is explicitly unmarked because it wraps (§4), and NO rule in the pass reads an =Assert=. Bounds propagate through producers only, so the one fact that makes the difference non-negative is invisible.

What the Pending lineage does about it, and the compat port cannot: =erc20_vault_pending::complete_swap= BUYS the bound with an extra instruction — =Uint::<64, Public>::from_field_checked(c, change.field())= at =erc20_vault_pending.rs:898=, commented in the source as "the taint lint's warrant for the 16-byte value atom", which lowers to the =constrain_bits 64= at instruction 176 right after the =add= at 175. The compat port is PI-equal to compactc and cannot add an instruction, so its difference reaches the coin commitment unbounded. ** Class B as built — N1, N2, N3

The structural problem §8 identified, restated: ZKIR v3 has no =Sub=, so =Uint::sub_with= lowers to =assert(ge(a, b)); n = neg(b); add(a, n)=, =Neg= wraps and is unmarked, and no rule read an =Assert=. Three rules now do, and ONLY for this shape. Pass A2 indexes the four shapes they must see through (=neg=, =not=, =cond_select=, =less_than=) and collects the =a ≥ b= facts the stream asserts; position-independent for pass A's reason, since an assert constrains the witness wherever it sits.

- *N1* =add(C, neg(b))= with =C= immediate and =Mb ≤ C= is the integer =C − b ∈ [0, C]=. No assert needed — the range constraint alone rules out the wrap. The precondition is TIGHT at the real site: =erc20_vault_pending='s =change_nonce= is =255 − mintNonce.hi= with =constrain_bits 8=, so =Mb = C = 255= exactly, and a 9-bit constraint correctly fails it. Pinned at that boundary.
- *N2* both operands inside the =less_than= width, plus an unconditional =a ≥ b=, gives =≤ Ma=.
- *N3* the same with the assert GUARDED, when both operands are =cond_select{a: x, b: 0, bit: g}= on the SAME =g=: with =g = 1= N2 applies, with =g = 0= both operands are exactly 0.

Both encodings of =NOT (a < b)= occur in the real streams and both are accepted: a =Not= instruction (=erc20_vault=) and =cond_select{a: 0, b: 1, bit: lt}= (=kernel_tokens=). Note these two shapes are ambiguous with N3's guarded-assert shape — both are a =cond_select= with =b: 1= — so =ge_fact= tries the unconditional reading FIRST and the guarded one only on failure. Getting that order wrong silently drops the =kernel_tokens= warrant and nothing else; it cost one test round.

Soundness direction held: a =less_than= narrower than its operands is not the comparison the rule reads it as and marks nothing; an assert naming another pair, or the same pair in the wrong order, marks nothing; an unbounded minuend marks nothing. =manager::execute='s three =%add= findings stay for exactly that last reason, which §8 called the right answer and which is the sharpest evidence the rules do not over-mark — the shape is N3's and only the precondition fails.

** Class A as built — option 4, the observability walk

The obligation §8 stated: the digest reaches the transcript only through Impacts guarded by =%g=, and reaches no =Assert= at all. Built as a forward closure from the read, with every consumer classified exhaustively and every unknown a refusal.

THE ONE THING §8 DID NOT ANTICIPATE, and the reason a naive reading of it fails: the publishing Impact's guard is NOT =%g=. In =erc20_vault::complete_deposit= the read sits under =%sel.65= and the coin commitment is pushed under =%sel.102 = cond_select(%mul.101, 0, %sel.65)= — a guard NESTED inside =%g=, which is what =when= does when it nests one arm in another. Requiring syntactic equality discharges nothing. The relation that is actually needed is DOMINANCE: =h= is zero whenever =g= is zero, which is true for =h = g= and through any chain of =cond_select{a: _, b: 0, bit: k}=. Syntactic and conservative; a guard that is semantically but not syntactically dominated marks nothing.

Sinks, and why each is a refusal rather than a pass:

- =Impact= with a variable guard: inert iff that guard is dominated by =g=. With an IMMEDIATE guard: never — it publishes whatever =g= does.
- =Assert=, =ConstrainEq=, =ConstrainBits=, =ConstrainToBoolean=: a forged value then changes whether the circuit is SATISFIABLE. That may well be safe, but it is a different argument and this rule does not make it.
- =Output=: leaving the circuit named is an effect of its own.
- =PublicInput= / =PrivateInput=: the only way these read a tainted wire is as their GUARD, which steers the transcript WALK — how many elements are consumed. Observable even though the arm ignores the guard in-circuit.
- everything else only computes, and whatever it binds is already in the closure.

The walk reads operands through =passes::operands= + =passes::returned= and definitions through =passes::defined_identifiers= rather than restating the match: those three are exhaustive by construction AND are the lists =tests/lean_dataflow.rs= diffs against =MinocrabZkir.Dataflow=, so a new upstream operand position cannot hide from the walk. They clone, so =Flow= precomputes reads/defines once per circuit instead of inside the fixpoint.
